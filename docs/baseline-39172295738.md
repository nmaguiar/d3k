## Security comparison and its limits

Trivy `0.76.0` was digest-pinned. Within each job, candidate and controls used the
same frozen databases. Both architecture jobs also used identical database bytes:

- Vulnerability DB SHA-256: `854a708cd5033f5bbac9b14a8252d49dedf02ebb9a79d002ff7945c299ea5bdd`.
- Java DB SHA-256: `0d62078f6b8e19f3d73c02a94835391b12298865228ba0e9087699921dcd79f4`.

Metadata hashes differ because download timestamps differ; the DB file hashes
above match. Raw scanner version, database metadata/hashes and reports are in
each retained artifact.

Outer candidate finding occurrences were identical on both architectures:

| Category | HIGH | CRITICAL | Fixable HIGH/CRITICAL | Unfixed HIGH/CRITICAL |
|---|---:|---:|---:|---:|
| OS | 155 | 7 | 0 | 162 |
| Go binaries | 40 | 0 | 36 | 4 |
| Java/JAR | 0 | 0 | 0 | 0 |

Both comparison reports have an empty `newFixableHighCritical` array. The original
three buildx **stdlib** findings are absent with real module coverage. Other
findings remain visible; findings from nested images are separate raw reports,
and scan execution success does not mean those images have zero vulnerabilities.
Counts are occurrences rather than unique CVEs or proof of exploitability.

The published reference scan identifies Ubuntu 26.04. The fresh historical-source
control is labelled Ubuntu by its build process, but Trivy identifies its result
as Debian `forky/sid` and reports zero OS HIGH/CRITICAL findings. This discrepancy
and OS package/advisory coverage require review before claiming distribution-level
CVE reduction. The fresh control also uses mutable historical installers and
explicitly repaired `adduser` installation. Gate success means no new fixable
findings under those recorded inputs and scanner interpretation, not equal
coverage or proof that Debian is less vulnerable overall.
